## 1. Overview — The Three Task Types

SelfUp's entire task layer is built on **three and only three** core task types. Every task in the system — whether created by the user, generated by AI, injected by the Fitness module, or assigned by a Quest — maps to one of these three types.

| Type | Purpose | Resets | Priority | Subtasks | HP Impact | XP on Miss |
|------|---------|--------|----------|----------|-----------|------------|
| **Dailies** | Day-to-day recurring actions | Every midnight | Yes | Yes | None | XP penalty (priority-based) |
| **Habits** | Long-term behaviour building | Daily / Weekly / Monthly | No | No | HP damage | None |
| **To-Do** | One-time extra work items | Never (one-shot) | Yes | Yes | None | XP penalty if overdue (priority-based) |

> **Core rule — XP is awarded exactly once per task on completion. No task ever gives XP twice, regardless of which module created it.**

## 2. Dailies

### 2.1 What Are Dailies?
Dailies are tasks that **reset every midnight**. They represent the player's standard daily protocol — the things they intend to do every day or on a fixed-duration schedule. If a Daily is not completed before midnight, it is marked as **Missed** and the player receives an XP penalty scaled to the task's priority.

Dailies are the engine of the daily loop. They are the first thing the player sees when they open the app and they define the rhythm of the game.

### 2.2 Who Creates Dailies?

| Source | Description |
|--------|-------------|
| **User** | Player manually creates a Daily from the dashboard or Time module |
| **AI / Gemma** | Auto-scheduling generates Dailies during morning planning or Auto-Sync |
| **Fitness module** | A running plan, workout plan, or diet protocol injects Dailies for its duration |
| **Skills module** | A skill roadmap injects daily practice sessions as Dailies |
| **Style module** | Style goals inject daily outfit-check or style-habit Dailies |
| **Quest system** | Some quests inject supporting Dailies to help the player complete them |

### 2.3 Daily Properties

| Property | Type | Required | Notes |
|----------|------|----------|-------|
| `id` | UUID | Yes | |
| `user_id` | UUID | Yes | |
| `title` | string | Yes | Max 100 chars |
| `description` | string | No | Optional detail |
| `priority` | enum | Yes | `low` / `medium` / `high` / `critical` |
| `category` | enum | Yes | `general` / `fitness` / `skills` / `style` / `system` |
| `source` | enum | Yes | `user` / `ai` / `fitness` / `skills` / `style` / `quest` |
| `scheduled_time` | time | No | Optional. If set, appears on calendar |
| `repeat_type` | enum | No | `daily` (default) / `weekly`. If `weekly`, `repeat_days` is required |
| `repeat_days` | array | No | Days of week to be active, e.g. `["mon","wed","fri"]`. Only used when `repeat_type = 'weekly'` |
| `expires_on` | date | No | For module-injected Dailies with a plan end date |
| `subtasks` | JSONB | No | Array of subtask objects |
| `is_completed` | boolean | Yes | Resets to false every midnight |
| `completed_at` | timestamp | No | Set on completion, cleared on reset |
| `xp_reward` | integer | Yes | Set by priority (see §5) |
| `xp_penalty` | integer | Yes | Set by priority (see §5) |
| `created_at` | timestamp | Yes | |

### 2.4 Daily Lifecycle

```
Created (by user / AI / module)
       ↓
Active — available for completion today
       ↓
[Midnight check]
  ├── Completed → Award XP → Reset to Active for next day
  │              (if expires_on reached → mark Finished, remove from list)
  └── Not completed → Apply XP penalty → Reset to Active for next day
```

### 2.5 Weekly Repeat Dailies
A Daily can be set to repeat only on **specific days of the week** instead of every day. This covers use cases like "Go to gym — Mon, Wed, Fri" or "Weekly review — Sunday only."

- `repeat_type = 'weekly'` + `repeat_days = ["mon","wed","fri"]`
- On days not in `repeat_days`, the Daily is **inactive** — it does not appear in the panel and cannot be missed or penalised.
- On active days it behaves identically to a standard Daily (resets at midnight, XP reward and penalty apply).
- The midnight reset job checks `repeat_days` before applying any penalty — no penalty fires on inactive days.

**Example — Gym 3 Days a Week:**
```
repeat_type: 'weekly'
repeat_days: ["mon", "wed", "fri"]
priority: 'high'

Monday midnight:   active → missed? → –10 XP penalty
Tuesday midnight:  inactive → no action
Wednesday midnight: active → missed? → –10 XP penalty
```

### 2.6 Fixed-Duration Dailies (Module-Injected)
When a module creates a plan with a defined duration, it injects Dailies that carry an `expires_on` date. These behave identically to normal Dailies but auto-remove from the active list when the plan ends.

**Example — 7-Day Running Plan:**
- Days 1–7: "Morning Run" appears in Dailies every day
- Each midnight the Daily resets to active for the next day
- After Day 7 midnight: all injected Dailies are marked `finished` and removed
- The plan is shown as Completed inside the Fitness module with a reward

## 3. Habits

### 3.1 What Are Habits?
Habits are **behaviour-building tasks**. Unlike Dailies (which are about getting things done today), Habits are about building consistent patterns over weeks and months. They have their own reset counter, they track streaks independently, and missing them damages HP — not XP.

Habits have **no priority level**. By definition, if something is a habit it is always important. Priority is not applicable.

### 3.2 Habit Reset Types
The user selects how often the habit resets when creating it:

| Reset Type | Resets At | Example |
|------------|-----------|---------|
| **Daily** | Every midnight | "Drink 3L of water" |
| **Weekly** | Every Monday midnight | "Go to the gym 4× this week" |
| **Monthly** | 1st of each month, midnight | "Read 1 book this month" |

### 3.3 Habit Duration — Finite vs Indefinite
When creating a habit, the user chooses one of two modes:

- **Indefinite** — the habit runs forever until the user manually pauses or deletes it.
- **Finite** — the habit runs for a defined number of days/weeks/months (e.g., a 30-day challenge). When the duration ends the habit is marked **Completed** and a final reward is issued.

### 3.4 Habit Properties

| Property | Type | Required | Notes |
|----------|------|----------|-------|
| `id` | UUID | Yes | |
| `user_id` | UUID | Yes | |
| `title` | string | Yes | Max 100 chars |
| `description` | string | No | |
| `category` | enum | Yes | `general` / `fitness` / `skills` / `style` / `system` |
| `reset_type` | enum | Yes | `daily` / `weekly` / `monthly` |
| `is_indefinite` | boolean | Yes | If false, `end_date` is required |
| `end_date` | date | No | Required if `is_indefinite = false` |
| `current_streak` | integer | Yes | Increments on each successful reset cycle |
| `longest_streak` | integer | Yes | All-time best streak for this habit |
| `is_completed_this_cycle` | boolean | Yes | Resets each cycle |
| `xp_reward` | integer | Yes | Fixed 10 XP (no priority) |
| `hp_penalty` | integer | Yes | Based on reset type (see §5) |
| `source` | enum | Yes | `user` / `ai` / `fitness` / `skills` / `style` |
| `created_at` | timestamp | Yes | |

### 3.5 Habit Lifecycle

```
Created → Active
       ↓
[Reset cycle check (daily / weekly / monthly)]
  ├── Completed → +XP → Streak +1 → Reset for next cycle
  │   └── end_date reached? → mark Finished → award completion bonus
  └── Not completed → -HP → Streak resets to 0 → Reset for next cycle
      └── Streak Freeze used? → no HP penalty, streak preserved
```

### 3.6 Habit Streak Tracking
Every habit tracks its own independent streak. The **composite Habits Streak** shown on the dashboard counts consecutive days where all active daily-reset habits were completed.

- Missing one habit resets the composite streak but not the streaks of habits that were completed.
- Individual habit streaks only reset when that specific habit is missed.

## 4. To-Do

### 4.1 What Are To-Dos?
To-Dos are **one-time tasks**. They do not reset. Once completed they are permanently marked done. They represent extra work, personal projects, errands, or anything that is not part of the daily routine.

To-Dos are the most flexible type — they support subtasks, priority, optional due dates, and optional calendar scheduling. If a To-Do has a `due_date` and is not completed by that date, it enters **Overdue** state and begins accumulating an XP penalty each day it remains incomplete.

### 4.2 To-Do Properties

| Property | Type | Required | Notes |
|----------|------|----------|-------|
| `id` | UUID | Yes | |
| `user_id` | UUID | Yes | |
| `title` | string | Yes | Max 100 chars |
| `description` | string | No | |
| `priority` | enum | Yes | `low` / `medium` / `high` / `critical` |
| `category` | enum | Yes | `general` / `fitness` / `skills` / `style` / `system` |
| `source` | enum | Yes | `user` / `ai` / `quest` |
| `due_date` | date | No | Optional deadline |
| `scheduled_time` | time | No | Optional. If set, appears on calendar |
| `subtasks` | JSONB | No | Array of subtask objects |
| `is_completed` | boolean | Yes | Set permanently on completion |
| `completed_at` | timestamp | No | |
| `xp_reward` | integer | Yes | Set by priority (see §5) |
| `xp_penalty` | integer | Yes | Set by priority (see §5). Applied per day once overdue |
| `created_at` | timestamp | Yes | |

### 4.3 To-Do Lifecycle

```
Created → Active (appears in To-Do panel)
       ↓
User completes it → Award XP → Mark Completed permanently
       ↓
Moves to Completed archive (viewable, not in active list)

If due_date passes without completion:
       ↓
Status → Overdue (red badge)
       ↓
Each midnight while overdue → Apply XP penalty (priority-based, see §5)
       ↓
User completes it → Award XP → Mark Completed (penalty stops)
```

To-Dos **without** a `due_date` have no penalty at all — they are genuinely optional open tasks with no time pressure.

### 4.4 Subtask Structure
Both Dailies and To-Dos support subtasks. Subtasks are stored as JSONB. Only the **parent task** awards XP — subtasks do not give XP individually.

```typescript
subtasks: [
  { id: "sub_1", title: "Research topic", is_completed: false },
  { id: "sub_2", title: "Write outline", is_completed: false },
  { id: "sub_3", title: "Final review", is_completed: false }
]
```

By default, a task can be marked complete even if subtasks are incomplete. Users can toggle a "require all subtasks" option per task if they want a hard gate.

## 5. XP & HP Economy Per Task Type

### 5.1 XP Rewards — Priority-Based

XP earned on completion is determined by **priority level**. This applies to Dailies and To-Dos. Habits have a fixed XP reward with no priority.

| Task Type | Priority | XP Earned | XP Penalty (if missed / overdue) |
|-----------|----------|-----------|----------------------------------|
| **Daily** | Low | 5 XP | –3 XP |
| **Daily** | Medium | 10 XP | –5 XP |
| **Daily** | High | 20 XP | –10 XP |
| **Daily** | Critical | 35 XP | –50 XP |
| **Habit** | — (no priority) | 10 XP | No XP penalty (HP penalty instead) |
| **To-Do** | Low | 5 XP | –5 XP / day while overdue |
| **To-Do** | Medium | 10 XP | –10 XP / day while overdue |
| **To-Do** | High | 20 XP | –20 XP / day while overdue |
| **To-Do** | Critical | 35 XP | –30 XP / day while overdue |

> **To-Dos without a `due_date` have zero penalty.** The overdue XP penalty only activates once a due date is set and passed.

> **No daily XP penalty ceiling.** Each missed Daily and each overdue To-Do applies its penalty individually. There is no cap on total daily XP loss — a player who neglects all their tasks will feel the full weight of that.

### 5.2 HP Impact — Habits Only

HP damage is exclusively triggered by **missed Habits**. Dailies and To-Dos never affect HP.

| Event | HP Change |
|-------|-----------|
| Habit missed — daily reset | –5 HP |
| Habit missed — weekly reset | –10 HP |
| Habit missed — monthly reset | –15 HP |
| Streak Freeze used | 0 HP (no penalty, streak preserved) |

> **No HP damage cap.** Every missed Habit costs HP individually. A player with 10 active daily habits who misses all of them loses 50 HP in one day. This is intentional — maintaining many habits should feel seriously costly to neglect. VIT attribute reduces per-hit damage (every 3 VIT points = 10% damage reduction) but does not cap total daily damage.

### 5.3 Attribute Multipliers on Task XP

RPG attribute bonuses apply on top of base XP when the task category matches.

| Task Category | Attribute Bonus |
|---------------|----------------|
| `fitness` | +0.5% XP per STR point |
| `skills` | +0.5% XP per INT point |
| `general` / `style` / `system` | No multiplier |

**Example:** A High priority Daily with `category: fitness` at STR 10 awards `20 × (1 + 0.005 × 10) = 21 XP`.

### 5.4 One XP Per Task — Enforced
If a Fitness module injects a Daily, that task awards XP once when completed — through the standard task XP system. The Fitness module does not separately award XP for the same action. This is enforced at the database level via a unique constraint on the XP transactions table (see §10).

## 6. Cross-Module Task Injection

When the user starts a plan in the Fitness, Skills, or Style modules, that module injects tasks into the main task system. The injection type (Daily, Habit, or To-Do) depends on the nature of the action.

### 6.1 Fitness Module → Task Injection

| Fitness Action | Injected As | Priority | Duration |
|----------------|-------------|----------|----------|
| Daily workout plan (e.g., 7-day running plan) | Daily | `high` | For plan duration, then auto-removed |
| Ongoing workout routine (no end date) | Habit (daily) | — | Indefinite |
| Daily water intake target | Habit (daily) | — | Indefinite |
| Daily calorie/macro logging | Habit (daily) | — | Indefinite |
| Weekly gym target (e.g., 4× per week) | Habit (weekly) | — | User-defined |
| One-off fitness goal (e.g., "Run a 5K") | To-Do | `high` | One-time |

**Fixed-Duration Plan Example — 7-Day Running Plan:**
1. User starts the plan in the Fitness module.
2. System creates a Daily titled "Morning Run" with `expires_on` = Day 7 and `source = 'fitness'`.
3. Daily resets each midnight for 7 days.
4. After Day 7 midnight, the Daily is marked `finished` and removed from the active list.
5. The Fitness module marks the plan as Completed and issues a reward.

### 6.2 Skills Module → Task Injection

| Skills Action | Injected As | Priority | Duration |
|---------------|-------------|----------|----------|
| Daily practice session (from roadmap) | Daily | `medium` | For roadmap phase duration |
| Ongoing daily practice habit | Habit (daily) | — | Indefinite or finite |
| Skill milestone (e.g., "Complete JS Basics") | To-Do | `high` | One-time |
| Weekly skill hours target | Habit (weekly) | — | User-defined |

### 6.3 Style Module → Task Injection

| Style Action | Injected As | Priority | Duration |
|--------------|-------------|----------|----------|
| Daily outfit log | Habit (daily) | — | Indefinite |
| Style challenge (e.g., "New aesthetic for 7 days") | Daily | `low` | For challenge duration |
| One-off style task (e.g., "Buy new shoes") | To-Do | `low` | One-time |

### 6.4 Deduplication Rule
If the AI or a module tries to inject a task that is functionally identical to an existing active task for the same user, the system updates the existing task instead of creating a duplicate.

```typescript
async function injectTask(userId, taskData) {
  const existing = await findActiveTask(userId, {
    title: taskData.title,
    category: taskData.category,
    source: taskData.source
  })
  if (existing) {
    return updateTask(existing.id, taskData)
  }
  return createTask(userId, taskData)
}
```

## 7. Quest Layer

### 7.1 What Are Quests?
Quests are a **motivational overlay** on top of the three task types. They are not a fourth task type. Quests track progress across task completions and reward players for completing patterns of behaviour.

A quest like *"Complete 5 workouts this week"* does not create 5 workout tasks. It watches the task system and counts fitness-category Daily/Habit completions. When the count hits 5, the quest completes and issues its reward.

### 7.2 Quest Sources

| Source | Description |
|--------|-------------|
| **Prebuilt** | Fixed templates built into the system (see gamification doc §6.3) |
| **AI-generated** | Gemma generates personal quests based on the user's weak points and recent behaviour |

### 7.3 How Quests Interact With Tasks

```
User completes a task (Daily / Habit / To-Do)
       ↓
Task completion event fires
       ↓
Quest engine checks: does this completion satisfy any active quest requirement?
  ├── Yes → increment quest progress
  │         └── Quest complete? → issue XP + AiCoins + badge reward
  └── No  → no quest action taken
```

Quests never block task completion. A task is always completable regardless of quest state.

### 7.4 Quest Rewards Are Additive
Quest XP rewards stack on top of task XP rewards. Completing a High priority Daily gives 20 XP from the task. If that completion also finishes a quest, the quest gives an additional 50–300 XP. Quests should feel like a bonus discovery — not the primary driver.

## 8. Calendar & Scheduling

### 8.1 Which Tasks Appear on Calendar?

| Task Type | Can be scheduled? | Calendar behaviour |
|-----------|-------------------|-------------------|
| **Daily** | Optional | Appears as a time block on the day it is active |
| **Habit** | No | Never on calendar — tracked via the Habits panel only |
| **To-Do** | Optional | Appears on the `due_date` at the `scheduled_time` |

### 8.2 AI Auto-Scheduling (Auto-Sync)
Costs 5 AiCoins. Gemma analyses all active Dailies and To-Dos without a scheduled time and assigns them to time slots. The AI considers:
- Work/study hours configured by the user
- Do Not Disturb hours
- Task priority (critical tasks get morning prime slots)
- Estimated duration (user-defined per task)
- Energy patterns inferred from past behaviour

### 8.3 Calendar Views

| View | Content |
|------|---------|
| **Day View** | All scheduled Dailies and To-Dos as time blocks |
| **Week View** | Overview of scheduled tasks for the week |
| **Month View** | To-Do due dates + habit completion heatmap (GitHub-style) |

Habits are shown as a heatmap row in the month view, not as calendar events.

## 9. Dashboard Panel Layout

The dashboard shows all three task types in **three separate side-by-side columns**. The frontend owns design and positioning. This section defines the data contract for each panel.

### 9.1 Dailies Panel
**Data:** All active Dailies for today, ordered by priority (critical → high → medium → low).

Each item shows: title, priority badge, category icon, XP reward, completion checkbox, scheduled time (if set), midnight countdown timer.

**Footer:** `X / Y completed today`

### 9.2 Habits Panel
**Data:** All active Habits, ordered by reset type (daily first, then weekly, then monthly).

Each item shows: title, current streak counter, reset type badge, completion checkbox, progress within cycle (e.g., "3/7 days"), HP warning if approaching end of day uncompleted.

**Footer:** Composite Habits Streak counter + `X / Y completed this cycle`

### 9.3 To-Do Panel
**Data:** All incomplete To-Dos, ordered by priority then by due date.

Each item shows: title, priority badge, category icon, XP reward, due date (red if overdue), subtask count (e.g., "2/3 done"), completion checkbox.

**Footer:** `X tasks remaining` + quick-add button

## 10. Database Schema

```sql
-- DAILIES
CREATE TABLE dailies (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id         UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title           TEXT NOT NULL,
  description     TEXT,
  priority        TEXT NOT NULL CHECK (priority IN ('low','medium','high','critical')),
  category        TEXT NOT NULL DEFAULT 'general'
                    CHECK (category IN ('general','fitness','skills','style','system')),
  source          TEXT NOT NULL DEFAULT 'user'
                    CHECK (source IN ('user','ai','fitness','skills','style','quest')),
  repeat_type     TEXT NOT NULL DEFAULT 'daily' CHECK (repeat_type IN ('daily','weekly')),
  repeat_days     TEXT[] DEFAULT NULL,
  -- repeat_days examples: NULL (daily), '{"mon","wed","fri"}' (weekly specific days)
  -- valid values: 'mon','tue','wed','thu','fri','sat','sun'
  scheduled_time  TIME,
  expires_on      DATE,
  subtasks        JSONB DEFAULT '[]',
  is_completed    BOOLEAN NOT NULL DEFAULT false,
  completed_at    TIMESTAMPTZ,
  xp_reward       INTEGER NOT NULL,
  xp_penalty      INTEGER NOT NULL,
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- HABITS
CREATE TABLE habits (
  id                      UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id                 UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title                   TEXT NOT NULL,
  description             TEXT,
  category                TEXT NOT NULL DEFAULT 'general'
                            CHECK (category IN ('general','fitness','skills','style','system')),
  source                  TEXT NOT NULL DEFAULT 'user'
                            CHECK (source IN ('user','ai','fitness','skills','style')),
  reset_type              TEXT NOT NULL CHECK (reset_type IN ('daily','weekly','monthly')),
  is_indefinite           BOOLEAN NOT NULL DEFAULT true,
  end_date                DATE,
  current_streak          INTEGER NOT NULL DEFAULT 0,
  longest_streak          INTEGER NOT NULL DEFAULT 0,
  is_completed_this_cycle BOOLEAN NOT NULL DEFAULT false,
  completed_at            TIMESTAMPTZ,
  xp_reward               INTEGER NOT NULL DEFAULT 10,
  hp_penalty              INTEGER NOT NULL DEFAULT 5,
  -- hp_penalty by reset_type: daily=5, weekly=10, monthly=15
  created_at              TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- TO-DOS
CREATE TABLE todos (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id         UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  title           TEXT NOT NULL,
  description     TEXT,
  priority        TEXT NOT NULL CHECK (priority IN ('low','medium','high','critical')),
  category        TEXT NOT NULL DEFAULT 'general'
                    CHECK (category IN ('general','fitness','skills','style','system')),
  source          TEXT NOT NULL DEFAULT 'user'
                    CHECK (source IN ('user','ai','quest')),
  due_date        DATE,
  scheduled_time  TIME,
  subtasks        JSONB DEFAULT '[]',
  is_completed    BOOLEAN NOT NULL DEFAULT false,
  completed_at    TIMESTAMPTZ,
  xp_reward       INTEGER NOT NULL,
  xp_penalty      INTEGER NOT NULL DEFAULT 0,
  -- xp_penalty only fires per-day once due_date is passed and task is incomplete
  -- penalty is 0 if no due_date is set
  created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- XP REWARD & PENALTY REFERENCE
-- ┌──────────────┬──────────┬─────────────┬─────────────────────────────────────┐
-- │ Task Type    │ Priority │ xp_reward   │ xp_penalty                          │
-- ├──────────────┼──────────┼─────────────┼─────────────────────────────────────┤
-- │ Daily        │ low      │ 5           │ –3 (on miss)                        │
-- │ Daily        │ medium   │ 10          │ –5 (on miss)                        │
-- │ Daily        │ high     │ 20          │ –10 (on miss)                       │
-- │ Daily        │ critical │ 35          │ –50 (on miss)                       │
-- │ Habit        │ n/a      │ 10 fixed    │ n/a (hp_penalty used instead)       │
-- │ To-Do        │ low      │ 5           │ –5 / day while overdue              │
-- │ To-Do        │ medium   │ 10          │ –10 / day while overdue             │
-- │ To-Do        │ high     │ 20          │ –20 / day while overdue             │
-- │ To-Do        │ critical │ 35          │ –30 / day while overdue             │
-- │ To-Do (no due_date) │ any │ by priority │ 0 (no penalty)               │
-- └──────────────┴──────────┴─────────────┴─────────────────────────────────────┘
-- NO daily XP penalty cap. All penalties apply individually.

-- XP TRANSACTION LOG (enforces one XP per task)
CREATE TABLE xp_transactions (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  source_type TEXT NOT NULL CHECK (source_type IN ('daily','habit','todo','quest','dungeon','streak','penalty')),
  source_id   UUID NOT NULL,
  amount      INTEGER NOT NULL,  -- positive = earned, negative = penalty
  reason      TEXT,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (source_type, source_id, user_id)  -- hard prevents double XP for same task
  -- Note: for recurring To-Do overdue penalties, source_id includes the date
  -- e.g. source_id = todo_uuid + ':' + date to allow one penalty per day per todo
);
```

## 11. Business Rules & Edge Cases

### 11.1 Midnight Reset Job
Runs at **00:01 AM** in the user's local timezone.

```
For each active Daily:
  - Check repeat_days: is today an active day?
    - No (weekly repeat, today not in repeat_days) → skip entirely, no action
    - Yes → continue
  - Completed → Award XP → Reset is_completed = false
  - Not completed → Apply XP penalty → Reset is_completed = false
  - expires_on <= today → Mark finished, remove from active list

For each active To-Do with due_date < today and is_completed = false:
  - Apply daily XP penalty (priority-based)
  - Log to xp_transactions with source_id = todo_id + ':' + today (one per day)

For each Habit with reset_type = 'daily':
  - Completed → +XP → current_streak++ → Reset is_completed_this_cycle = false
  - Not completed → -HP (no cap) → current_streak = 0 → Reset
  - end_date reached → Mark finished, issue completion bonus

Weekly habits: same logic, runs Monday midnight only
Monthly habits: same logic, runs 1st of month midnight only
```

### 11.2 Streak Freeze Behaviour on Habits
If a Streak Freeze is consumed when a Habit would be missed:
- No HP penalty applied
- Streak is preserved (not incremented, just held)
- `is_completed_this_cycle` is set to `'freeze_used'`
- AGI ≥ 10: freeze activates automatically at midnight
- AGI < 10: user must manually activate freeze before midnight

### 11.3 Module Plan Cancellation
If a user cancels a plan mid-way in Fitness/Skills/Style:
- All injected Dailies tied to that plan (`source = 'fitness'/'skills'/'style'` + matching `expires_on`) are immediately marked `finished` and removed from the active list
- Injected Habits remain active — the user must manually delete them
- XP already earned from completed injected tasks is kept permanently

### 11.4 Critical Task Urgency Notification
Any Daily or To-Do with `priority = 'critical'` that is still incomplete at **6:00 PM** local time fires a push notification:

> *"System Warning: Critical objective unresolved — {title}. {n} hours remain."*

### 11.5 AI Quest Listening (No Duplicate Tasks)
When an AI quest requires a specific task type (e.g., "Log 3 workouts this week"), the quest engine listens for matching task completions. It does not inject new tasks. The player satisfies the quest naturally through their existing Dailies and Habits.

### 11.6 To-Do Overdue Penalty
A To-Do past its `due_date` is flagged as **Overdue** (red date badge) and the midnight job applies a daily XP penalty until completed or deleted. The penalty is priority-based (Low=–5, Medium=–10, High=–20, Critical=–30 XP per day). To-Dos **without** a `due_date` never enter overdue state and have zero penalty.

### 11.7 Subtask Override
A Daily or To-Do with incomplete subtasks can still be marked complete. Users can optionally enable a "require all subtasks complete" toggle per task. This is off by default.
